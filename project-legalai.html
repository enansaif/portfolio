Legal AI Assistant

High-level Overview

An AI-driven legal assistant that provides accurate, location-specific legal information. It leverages location-aware search and trusted legal sources to deliver clear, cited responses, and guides users to official documentation for further reference.

Role & Responsibilities

Search & Retrieval System
  • Designed and implemented the query augmentation system for the citation engine, deciding how queries should be adapted for each task to get the best results.
  • Improved the vector search process to enhance citation accuracy by improving language model prompts, filtering out problematic data, and optimizing how final answers are generated using those citations.
Data Infrastructure
  • Designed the logic for storing vector data, including pre-processing steps, what metadata to store with each vector, and regional separation by country and state.
  • Designed a logging system to track every website the web scraper visited, failed to access, was blocked from, or ignored — all saved in a database for future reference.
  • Migrated away from a locally run vector database (FAISS) setup to Supabase with pg_vector (a postgresql extension that allows storing vector data) to address scalability, maintenance concerns and metadata filtering.
System Performance & Architecture
  • Optimized the AI’s response generation process to reduce latency by evaluating tools, external services, and choosing between AI agents (Re-Act agent with tools support) and custom-built approach.

Key Achievements

  • Successfully convinced management to transition away from the existing Re-Act based AI agent and instead focus on enhancing our custom retrieval workflow. Led the implementation, resulting in a 67% reduction (~90 seconds to ~30 seconds) in response times.
  • Implemented multithreading for parallel execution of independent API calls. This was one of the contributing factors to the overall response time reduction.
  • Identified problematic data sources (e.g., index pages and home pages) by analyzing vector database responses. Created a block list to exclude these sources, resulting in a 25% improvement in citation accuracy.
  • Discovered instability caused by using a single query augmentation method for both vector search and final response generation, developed a separate augmentation module for each process. This improved citation accuracy by 20%.
  • Found that inconsistent search results were caused by a speed-vs-accuracy tradeoff in the vector database’s filtering. Adjusted the search depth, improving citation accuracy by 15% with only a small increase in response time.

Design Decisions and Trade-offs

  • Why Supabase over self-hosted vector database (FAISS)?
    Chose Supabase over FAISS for better horizontal scalability, metadata filtering, and reduced maintenance complexity.
  • Why custom retrieval chain over AI agent with tools (Re-Act agent)?
    AI agents introduced unnecessary latency and unpredictable control flow. We opted for a deterministic chain with clear separation of search and generation phases, allowing better control and debugging.
  • Why two separate query augmentation functions?
    Using a single prompt for both vector search and LLM response generation degraded citation quality. Splitting these concerns allowed us to optimize each independently.

Challenges & Constraints

  • Limited legal data availability in certain states, requiring custom scraping pipelines and fallback logic.
  • No access to full legal databases due to licensing constraints — had to rely on public legal portals.
  • Latency expectations under 30s total response time despite complex document retrieval and parsing.

Mistakes & Learnings

1. Accidental Deletion of Admin Panel Data
  • Issue: Ran a volume-wiping command on the development server, causing loss of all admin panel data.
  • Root Cause: Misunderstood architecture—admin data in dev was not isolated like in prod.
  • Resolution: Migrated admin data to a separate DB in dev to mirror production.
  • Lesson: Confirm environment scope before executing infrastructure commands.
2. Broken Vector Index During Data Scraping
  • Issue: Mid-process crash corrupted the vector index in dev, degrading search results.
  • Root Cause: Scraper wrote directly to the live dev vector DB.
  • Resolution: Added staging vector DB to fully index before replacing the live DB.
  • Lesson: Never write directly to live query systems — stage and validate ingestion separately.

Technologies Used

Python, Django, PostgreSQL, pg_vector, Supabase, Faiss (legacy), Docker, AWS EC2, AWS RDS, Langchain (legacy), langgraph (legacy)
